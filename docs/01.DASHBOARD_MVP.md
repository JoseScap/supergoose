# SuperGoose Dashboard MVP

Documento de fase 01 para construir la primera experiencia visual de SuperGoose sobre el backend existente.

## Objetivo de la fase

Construir un dashboard frontend en React que permita explorar y entender lo que ya gestiona la API, sin introducir todavía operaciones de escritura desde la UI.

Esta fase define la base visual del producto para que todas las fases posteriores evolucionen sobre la misma estructura.

## Punto de partida

- La fase 00 ya existe como backend funcional.
- La API ya expone health, readiness, autenticación por API Key, gestión de projects y CRUD genérico por collection.
- El dashboard debe apoyarse en esa API y no duplicar lógica de negocio.

## Visión del producto

SuperGoose tendrá dos niveles de experiencia:

1. Dashboard general del cluster.
2. Dashboard de cada proyecto.

Ambos dashboards compartirán el mismo layout base con sidebar lateral.

El dashboard general servirá para ver y entrar a los proyectos del cluster.
El dashboard de proyecto servirá para explorar los datos de una base concreta mediante un data explorer similar al de MongoDB.

## Alcance funcional de la fase 01

- Aplicación frontend en React.
- Layout clásico con sidebar fijo a la izquierda.
- Área principal para navegación y contenido.
- Pantalla general del cluster con grilla de proyectos.
- Navegación hacia el dashboard de un proyecto.
- Dashboard de proyecto con un data explorer readonly.
- Consumo de la API existente para listar y mostrar información real.

## Dashboard general del cluster

La vista principal del dashboard mostrará el estado general del cluster y la lista de proyectos disponibles.

Debe permitir:

- Ver una grilla de proyectos.
- Identificar rápidamente nombre, slug y estado del proyecto.
- Entrar al dashboard de un proyecto desde su tarjeta o fila.
- Mostrar información útil para administración general del cluster.

En esta fase, la vista general es principalmente de lectura y navegación.

## Dashboard de proyecto

Al entrar en un proyecto se abre una vista específica de ese proyecto.

Debe permitir:

- Ver el contexto del proyecto seleccionado.
- Navegar collections disponibles.
- Explorar documentos de una collection.
- Inspeccionar el detalle de un documento.
- Filtrar, ordenar y paginar resultados desde la experiencia visual.

En esta fase, el dashboard de proyecto es readonly.
No incluye todavía crear, editar ni eliminar documentos desde la UI.

## Data Explorer

El data explorer será la pieza principal del dashboard de proyecto.

Debe comportarse de forma similar a un explorador de MongoDB, con foco en lectura y análisis.

Componentes esperados:

- Lista de collections.
- Tabla o grilla de documentos.
- Panel de detalle para un documento.
- Búsqueda y filtros básicos.
- Ordenamiento.
- Paginación.

La intención es que el usuario pueda recorrer datos reales de forma clara y rápida, sin perderse en una interfaz compleja.

## Estructura visual

La UI debe tener una estructura estable y extensible:

- Sidebar izquierdo para navegación principal.
- Header o top bar para contexto actual y acciones globales.
- Área central para el contenido principal.
- Estados vacíos y estados de carga bien definidos.

Este layout debe ser el mismo tanto para el dashboard general del cluster como para el dashboard de proyecto.
La diferencia entre ambos niveles debe estar en el contenido central, el contexto mostrado y las acciones disponibles.

La navegación debe distinguir con claridad entre:

- cluster dashboard
- project dashboard

## Integración con la API

La app frontend debe prepararse para consumir la API existente y mostrar datos reales.

Como mínimo, el dashboard debe contemplar:

- listado de proyectos;
- acceso a detalles del proyecto;
- exploración de collections y documentos;
- lectura del estado del backend cuando aplique.

La UI no debe asumir datos mock como base del producto final, aunque puede usar datos temporales durante el desarrollo visual si hace falta.

## Reglas de diseño para esta fase

- Evitar una interfaz genérica o indiferenciada.
- Mantener una jerarquía clara entre cluster y proyecto.
- Priorizar legibilidad y navegación sobre densidad visual.
- Diseñar pensando en fases futuras, no solo en la vista inicial.
- Dejar espacio para crecer hacia schemas, auth, permisos, storage y realtime.

## Fuera de alcance de la fase 01

- Crear o editar documentos desde el dashboard.
- Edición de schemas o modeling.
- Authentication flow para usuarios finales.
- Authorization granular en UI.
- Storage, realtime, webhooks o functions.
- Dashboards complejos por entidad no prevista.
- SDKs o generación de tipos.

## Resultado esperado

Al terminar esta fase, SuperGoose debe contar con una primera interfaz frontend que:

- se conecte al backend existente;
- muestre los proyectos del cluster;
- permita entrar a un proyecto;
- ofrezca un data explorer readonly;
- establezca la base visual sobre la que crecerán las siguientes fases.

## Orden recomendado de implementación

1. Definir el app shell y el layout base.
2. Construir la vista general del cluster.
3. Construir la navegación hacia un proyecto.
4. Implementar el dashboard de proyecto.
5. Integrar el data explorer readonly.
6. Refinar estados vacíos, loading y errores.
7. Ajustar accesibilidad, responsive y consistencia visual.
